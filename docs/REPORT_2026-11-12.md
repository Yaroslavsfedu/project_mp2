| Проблема | Исправление |
|---|---|
| Лимиты считались в памяти процесса: при `--workers 2` лимит на каждый воркер отдельно | Лимиты в **Redis** (фиксированное окно, INCR + EXPIRE), общие для всех воркеров и Celery |

### 4.4 Миграции PostgreSQL (итерация 2)

| Проблема | Исправление |
|---|---|
| Миграция `7c1a4f9e2b10` падала, если нет `pg_trgm` (нет `postgresql-contrib`): ошибка прерывала всю транзакцию | Проверка `pg_available_extensions`; необязательные шаги в **SAVEPOINT** (`begin_nested`); при отсутствии расширения — сообщение в лог, миграция проходит |

| Полнотекстовый поиск пересчитывал `to_tsvector` для каждой строки при ранжировании | Миграция `c3e8a1b5d7f9`: хранимый столбец `search_tsv` (GENERATED … STORED) и GIN-индекс; в `init_db` то же самое |

Проверено: чистая БД PostgreSQL 16 без `pg_trgm` → `alembic upgrade head` проходит; `downgrade -1` и повторный `upgrade head` тоже проходят. В логе миграции явно указано, что индекс по имени файла не создан.

### 4.5 Pyflakes (итерация 2)

`backend/app/core/database.py`: импорт `app.models` ради регистрации моделей помечен как неиспользуемый. Pyflakes не учитывает `# noqa` (это поведение flake8), поэтому импорт заменён на `importlib.import_module("app.models")`. Pyflakes по изменённым модулям чистый.

### 4.6 Производительность поиска (итерация 2)

| Проблема | Замер до | Исправление | Замер после |
|---|---|---|---|
| Полнотекстовый: `ts_headline` и `ts_rank` для всех совпадений | p95 430 мс | CTE: сначала top-N, `ts_headline` только для них | не помогло: p50 387 мс (узкое место — `to_tsvector` при ранжировании) |
| Полнотекстовый: `to_tsvector` при ранжировании | p95 468 мс | хранимый `search_tsv` + GIN | **p95 22 мс** |
| Семантический на SQLite: ORM загружал JSON-вектора всех чанков на каждый запрос | p95 408 мс | кэш нормализованных `float32`-векторов в памяти процесса + матричное умножение `numpy` | **p95 31 мс** |

Кэш векторов: ключ — UUID чанка (при переобработке чанки получают новые id, устаревших записей не возникает). Лимит 60 000 чанков (≈240 МБ при 1024 измерениях), при превышении кэш очищается.

### 4.7 Нестабильность тестов (итерация 2)

Наблюдалось `sqlite3.OperationalError: database is locked` (в одном прогоне — 2 failed, в другом — 1 failed). Первая гипотеза — таймаут: добавлен `timeout=30`, но прогоны стали длиться по 35 с (ожидание блокировки), а сбои остались. Причина — режим rollback-журнала SQLite: читающая транзакция держит блокировку SHARED и не даёт писателю перейти к записи, поэтому SQLite сразу возвращает BUSY, таймаут не помогает. Исправление: WAL (`PRAGMA journal_mode=WAL`) и `PRAGMA busy_timeout=30000` при каждом подключении. После этого 4 прогона подряд: 63 passed за ~5.5 с, без ожиданий.

Прежний разовый сбой (2 failed в итерации 1) с большой вероятностью имел ту же причину; прямо это не воспроизводилось, поэтому утверждаю только «вероятно».

### 11.3 Планы и поправка к FTS

Первый прогон выявил проблему: для частого слова планировщик выбрал `Seq Scan` по `ocr_pages` с ранним выходом
по LIMIT. Это быстро только тогда, когда слово встречается почти везде; при редком слове такой обход
пошёл бы по всей таблице (O(N)). Поправка: внутри FTS-запроса `enable_seqscan=off` (`gin_only` в `core/database.py`),
действует только в транзакции (`SET LOCAL`).

Замер на 100 000 страниц после поправки (`/tmp`, отдельный прогон; слова — синтетика):

| Слово | Стандартный план | `enable_seqscan=off` (gin_only) | Оба запрета (seq+index) |
|---|---|---|---|
| «договор» (100%) | 4.8 мс, Seq Scan | 2.3 мс, Index Scan по `document_id` | 13.1 мс, Bitmap GIN на 100k строк |
| «оригинал» (20%) | 4.9 мс, Seq Scan | 7.2 мс, Bitmap GIN | 7.9 мс, Bitmap GIN |
| «кварта» (2%) | 4.0 мс, Bitmap GIN | 3.5 мс, Bitmap GIN | 3.2 мс, Bitmap GIN |
| «редкийтермин» (20 строк) | 0.8 мс, Bitmap GIN | 0.9 мс, Bitmap GIN | 0.8 мс, Bitmap GIN |

Вывод: на замеренных данных `gin_only` не даёт гарантированного выигрыша (на «оригинале» немного медленнее).
Он оставлен как защита от плохого плана при большом числе строк: оценки селективности `@@` в PostgreSQL грубые,
и на 2 млн страниц выбор Seq Scan для слова средней частоты стал бы дорогим. Риск не проверен на 2 млн
и отмечен в ограничениях. Отдельная проверка: гипотеза «обход по свежим документам ускорит частое слово» не
подтвердилась (68 мс против 4.6 мс у GIN), поэтому такой путь не внедрён.

Сноска по данным: «редкийтермин» — 20 страниц из 100 000, «оригинал» — 20%, «договор» — 100%.

### 11A.4 FTS5 (SQLite): разбор 118 мс и что изменено

**Причина.** `ORDER BY bm25 LIMIT N` считает bm25 по всем совпадениям запроса, а JOIN и `snippet()` до `LIMIT` почти
бесплатны. Для частого слова (совпадает почти с каждым чанком) стоимость — это bm25 по сотням тысяч строк.

**Вариант, внедрён.** Двухшаговый путь без фильтров (`search_service._fts5_two_step`): (1) FTS5 `ORDER BY bm25 LIMIT N`
без JOIN; (2) текст выбранных `rowid` из `document_chunks` и `make_snippet` в Python. С фильтрами остаётся прежний
JOIN-запрос. Тест `test_fts5_two_step_order_matches_joined_path` проверяет, что порядок результатов двух путей совпадает.

| Терм (100k чанков), p95, мс | JOIN (был) | Двухшаговый (стал) | LIKE (без ранжирования) |
|---|---|---|---|

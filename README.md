# IDP Platform — оцифровка и обработка документов

Веб-приложение для загрузки, распознавания и обработки документов (IDP) с **полностью локальной**
обработкой: OCR, извлечение сущностей через локальную LLM (Ollama), поиск, ручная верификация и экспорт.
Внешние платные API не используются.

Проект ИКТИБ ЮФУ (Проектный офис). Спецификация: [`AI/context/project.md`](AI/context/project.md).

---

## Что умеет

- Загрузка PDF, JPG, PNG, TIFF, DOCX, TXT — пакетно, до 50 МБ на файл; проверка по сигнатуре файла (magic bytes).
- Извлечение текста: текстовый слой PDF и DOCX; для сканов — OCR (Tesseract или локальная VLM через Ollama).
- Препроцессинг сканов: выравнивание наклона, удаление синих печатей, бинаризация, поворот 0/90/180/270.
- LLM (Ollama, `qwen2.5:7b-instruct`): коррекция OCR, классификация типа, извлечение сущностей (ФИО, организации,
  даты, суммы, ИНН/ОГРН, адреса), резюме, строгий JSON. Если Ollama недоступна — включается
  эвристический fallback (регулярные выражения и правила).
- Поиск: полнотекстовый, семантический (эмбеддинги `bge-m3`) и гибридный, с фильтрами.
- Split-Screen верификация: скан с подсветкой слов ↔ текст ↔ форма сущностей; статус «проверено».
- Вопросы по документу (RAG-чат) с указанием фрагментов-источников.
- Экспорт: JSON, CSV, DOCX, TXT, Markdown; пакетный экспорт CSV и XLSX.
- Статусы обработки в реальном времени (WebSocket), журнал аудита, роли admin / operator / viewer.

Подробный список соответствия ТЗ и известные отклонения — в разделе [«Соответствие ТЗ»](#соответствие-тз).

## Установка

### 1. Скачайте проект

```bash
git clone https://github.com/Yaroslavsfedu/project_mp2.git
cd project_mp2
```

### 2. Запустите установщик

```bash
./scripts/bootstrap.sh
```

Скрипт идемпотентен (повторный запуск безопасен) и делает следующее:

1. проверяет Python 3.11+ и Node.js 20+;
2. создаёт виртуальное окружение `backend/.venv` и ставит зависимости;
3. создаёт `.env` из `.env.example` и генерирует случайный `SECRET_KEY`;
4. создаёт базу SQLite `backend/data/idp.db` и применяет миграции;
5. генерирует демо-документы в `samples/`;
6. ставит зависимости фронтенда (`npm`);
7. показывает итоговую проверку окружения (`scripts/check_env.py`).

Если нужна локальная LLM, сначала установите [Ollama](https://ollama.com), затем:

```bash
./scripts/bootstrap.sh --models    # то же + скачивание моделей (несколько ГБ)
```

Модели подбираются по объёму видеопамяти (`scripts/pull_models.sh`): 7B при 8+ ГБ VRAM, 3B или 1.5B на CPU.
Эмбеддинги `bge-m3` и VLM для сканов (`qwen2-vl:7b`, включается флагом `WITH_VISION=1`) тоже скачиваются этим скриптом.

### 3. Запустите приложение

```bash
make dev
```

| Адрес | Что там |
|---|---|
| http://localhost:5173 | веб-интерфейс |
| http://localhost:8000/api/docs | Swagger (API) |

Вход: **demo@idp-project.ru / demo12345** — демо-пользователь с ролью admin.

Запуск по частям: `make api` (только backend) и `make web` (только frontend) в двух терминалах.

### 4. Проверка

```bash
make check       # окружение: Python, Node, GPU, Ollama, Tesseract
make test        # автотесты backend
make evaluate    # качество распознавания и извлечения на демо-датасете
```

### Установка вручную (без скрипта)

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cd .. && cp .env.example .env
cd backend && PYTHONPATH=. alembic upgrade head && cd ..
(cd frontend && npm install)
make dev
```

## Настройка (.env)

Файл `.env` лежит в **корне проекта**. Основные параметры:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SECRET_KEY` | генерируется установщиком | подпись JWT. **Обязательно замените при общем доступе** |
| `DATABASE_URL` | SQLite в `backend/data/idp.db` | для PostgreSQL: `postgresql+asyncpg://user:pass@host/db` |
| `OLLAMA_URL` | `http://localhost:11434` | адрес Ollama |
| `OLLAMA_MODEL` | `qwen2.5:7b-instruct` | LLM |
| `EMBEDDING_MODEL` / `EMBEDDING_DIM` | `bge-m3` / `1024` | эмбеддинги; размерность должна совпадать с моделью |
| `LLM_FALLBACK_ENABLED` | `true` | эвристики, если LLM недоступна |
| `OCR_ENGINE` | `auto` | `auto` · `tesseract` · `ollama` (VLM) · `native` (только текстовый слой) |
| `QUEUE_BACKEND` | `inline` | `inline` — фоновые задачи в процессе API; `celery` — отдельный воркер + Redis |
| `RATE_LIMIT_ENABLED` | `true` | лимиты на вход (10/мин) и загрузку (30/мин) с одного IP |
| `TRUST_PROXY_HEADERS` | `false` | учитывать `X-Forwarded-For` — **включайте только за своим reverse-proxy** (в Docker включено для nginx) |
| `RATE_LIMIT_BACKEND` | `auto` | лимиты в Redis (общие для воркеров); при недоступности Redis — память процесса |

Полный список с комментариями — в [`.env.example`](.env.example).

## OCR для сканов

Текстовый слой PDF, DOCX и TXT распознаются без OCR. Для сканов и фото нужен один из движков:

- **Tesseract** (CPU, быстро, есть координаты слов):
  - Ubuntu/Debian: `sudo apt install tesseract-ocr tesseract-ocr-rus`
  - macOS: `brew install tesseract tesseract-lang`
  - Windows: установщик UB-Mannheim, при установке выберите русский язык
- **VLM через Ollama** (GPU, лучше для фото, наклонов и рукописи): `WITH_VISION=1 ./scripts/pull_models.sh`,
  затем в `.env`: `OCR_ENGINE=ollama`.

Без OCR скан получает статус `failed` с понятным сообщением, остальные документы обрабатываются.

## Проверка качества

Метрики на эталонном демо-датасете (`samples/ground_truth.json`), отчёт: [`reports/quality/quality.md`](reports/quality/quality.md).

| Метрика | Значение | Цель ТЗ |
|---|---|---|
| CER (символы) | 0.02 % | ≤ 3 % |
| WER (слова) | 0.19 % | ≤ 8 % |
| NER F1 | 98.97 % | ≥ 85 % |
| Точность классификации | 100 % | ≥ 90 % |

**Важно:** эти цифры получены на синтетических документах с текстовым слоем и на fallback-движке
(без OCR и без LLM). Качество на реальных сканах и с моделью Qwen нужно измерить на вашем оборудовании:
`make evaluate` с включённой Ollama и сканами в эталонной выборке.

Скорость и нагрузка: `make benchmark` (`reports/benchmark.json`) и `make load-test COUNT=50` (`reports/load_test.json`).

### Скорость поиска на 1000+ документах (ТЗ §13: < 200 мс)

`make search-bench` создаёт 1000 документов из реальных текстов демо-датасета (с чанками и эмбеддингами),
замеряет поиск в режимах fulltext / semantic / hybrid и удаляет тестовые данные. Отчёт — `reports/search_benchmark.json`.

| База | Режим | p95 на сервисном уровне | p95 через HTTP API |
|---|---|---|---|
| PostgreSQL 16 + pgvector | fulltext | 22 мс | 24 мс |
| PostgreSQL 16 + pgvector | semantic | 8 мс | 11 мс |
| PostgreSQL 16 + pgvector | hybrid | 30 мс | 34 мс |
| SQLite (по умолчанию) | semantic | 31 мс | — |

Замер выполнен на 2 vCPU без GPU, эмбеддинги — fallback (hashing). С bge-m3 через Ollama семантическая часть
добавит время на вычисление вектора запроса. Это время не измерялось и в замер не входит.

### Масштабируемость на 2+ млн документов (High-Load Architecture)

Цель (требование руководителя, итерация 3): рост базы в 50–100 раз не должен ломать отклик списка и поиска.
`make scale-bench` строит базу до 100 000 документов пакетной вставкой, замеряет p95 на каждом размере и пишет
`reports/scale_benchmark.json`. Порог: p95 < 100 мс на самом большом размере.

| Задача | Решение | Где в коде |
|---|---|---|
| Хранение файлов | Префиксное шардирование `uploads/ab/cd/{id}_{имя}` (2 уровня, как у Git objects): 65 536 листовых каталогов, ~30 файлов в каталоге на 2 млн. Старые файлы `originals/` читаются через `document_prefixes` | `services/storage_service.py` |
| Список документов | Keyset-пагинация по `(created_at, id)` (`cursor`), параметры `page/limit` сохранены; глубокий OFFSET ограничен `LIST_OFFSET_MAX` | `services/document_list_service.py`, `api/v1/documents.py` |
| Индексы документов | Составные B-Tree: `(status, doc_type, created_at DESC)` и `(created_at DESC, id)`; миграция `d5a1c9e3f7b2` | `models/document.py`, `alembic` |
| Итог по списку | Без фильтров при таблице ≥ `COUNT_ESTIMATE_THRESHOLD` (100 000) — оценка `pg_class.reltuples`; иначе точный `COUNT(*)`; результат кэшируется на `COUNT_CACHE_TTL_SECONDS` (30 с) | `document_list_service.py` |
| Полнотекстовый поиск | Bounded-отбор кандидатов: GIN по `search_tsv` с `LIMIT FTS_CANDIDATE_LIMIT` (2000); `ts_rank`/`ts_headline` только для них; `enable_seqscan=off` внутри FTS-запроса | `services/search_service.py`, `core/database.py` (`gin_only`) |
| Векторный поиск (PostgreSQL) | pgvector HNSW `m=16, ef_construction=64`, `hnsw.ef_search` задаётся на запрос; при `STORE_JSON_EMBEDDINGS=false` JSON-копия эмбеддингов на PostgreSQL не пишется (по умолчанию `true`) | `core/database.py`, `services/vector_store.py` |
| Векторный поиск (SQLite) | Вместо полного сброса кэша — LRU (`OrderedDict`, `VECTOR_CACHE_LIMIT=60000`) и батчевое чтение по id | `services/vector_store.py` |
| Пакетная загрузка | `make bulk-ingest`: поток файлов батчами 500–1000, пакетная вставка, контрольная точка для возобновления, пауза при очереди Celery/Redis выше порога (защита Redis от OOM) | `scripts/bulk_ingest.py` |

**Результаты замера** (PostgreSQL 16.2 + pgvector 0.6.2, 2 vCPU, 3 ГБ RAM песочницы, эмбеддинги случайные;
отчёт `reports/scale_benchmark.json`):

| Операция (p95) | 2 000 док. | 20 000 док. | 100 000 док. | Отношение 100k/2k |
|---|---|---|---|---|
| Первая страница списка | 2.1 мс | 2.4 мс | 2.3 мс | ~1× |
| Keyset-страница (середина) | 2.6 мс | 3.3 мс | 2.0 мс | ~1× |
| Keyset с фильтрами | 2.9 мс | 2.5 мс | 2.9 мс | ~1× |
| Оценка total без фильтров (`reltuples`) | 1.3 мс | 3.2 мс | 0.5 мс | константа |
| Глубокий OFFSET 50 000 | 2.0 мс | 10.5 мс | 25.9 мс | ~13× (растёт, O(offset)) |
| Точный COUNT с фильтром | 0.9 мс | 3.3 мс | 13.7 мс | ~16× (растёт) |
| Список с `q` (частое слово) | 10.9 мс | 15.9 мс | 35.2 мс | ~3× (растёт) |
| FTS, редкое слово (20 страниц из 100k) | 5.9 мс | 2.9 мс | 5.6 мс | ~1× |
| FTS, слово средней частоты (20%) | 3.9 мс | 2.5 мс | 18.5 мс | ~5× (растёт с числом совпадений) |
| FTS, частое слово (во всех страницах) | 14.8 мс | 23.3 мс | 27.1 мс | ~2× (ограничено LIMIT 2000) |
| Семантика (HNSW, k=20) | 3.7 мс | 3.9 мс | 3.0 мс | ~1× |
| Гибридный поиск | 10.2 мс | 4.7 мс | 28.9 мс | ~3× |

Вывод по замеру, без преувеличения: **константными (O(log N)) остаются первая страница, keyset-страницы
(с фильтрами и без), оценка total, FTS по редкому слову и HNSW-поиск**. Глубокий OFFSET, точный COUNT с фильтром,
список с `q` и поиск по частым словам растут с объёмом. На 100 000 документов все они укладываются в 100 мс,
но на 2 млн их нужно ограничивать (`LIST_OFFSET_MAX`, `COUNT_ESTIMATE_THRESHOLD`, `FTS_CANDIDATE_LIMIT`)
или отдавать через кэш; keyset-пагинация — рекомендуемый путь для глубоких страниц.
Замер на синтетических данных: «договор» есть во всех страницах, «редкийтермин» — в 20 из 100 000 страниц.
Цифры 20 000 и 2 000 в одном прогоне могут шуметь на 2 vCPU; тренд важнее отдельных значений.

**Расчёт ресурсов на 2 000 000 документов** (экстраполяция по измеренным байтам на 100 000 документов; допущения:
5 страниц и 10 чанков на документ, векторы 1024 float32, средний файл 200 КБ):

| Ресурс | Оценка | Комментарий |
|---|---|---|
| Таблица `documents` | ~1 ГБ | 542 байта на документ с индексами (измерено) |
| `ocr_pages` (10 млн страниц) | ~48 ГБ | ~5 КБ на страницу с текстом и tsvector — оценка |
| Чанки: текст + вектор (20 млн) | ~91 ГБ | вектор float32 4 КБ + служебные данные |
| HNSW-индекс (20 млн) | **~148 ГБ в RAM** | 7.9 КБ на чанк (измерено); `halfvec` ~74 ГБ — не проверено (нужен pgvector ≥ 0.7) |
| Оригиналы файлов | ~380 ГБ | файловая система, не БД |
| **Диск, итого** | **~290 ГБ БД + ~380 ГБ файлов + запас на WAL и бэкапы** | рекомендуется ≥ 1 ТБ SSD |
| **RAM** | HNSW ~148 ГБ + shared_buffers 16–32 ГБ + воркеры 4–8 ГБ | для стабильной задержки HNSW целиком в RAM нужен сервер ~192 ГБ RAM |
| **CPU, индекс HNSW** | ~40 мин на одном ядре (линейная экстраполяция по 100 000) | параллельная сборка pgvector сокращает время |
| **CPU, загрузка строк** | ~5 мин (только строки, без OCR) | OCR и LLM — узкое место: ~220 док/мин на 2 ядрах (`reports/benchmark.json`), то есть на 2 млн нужны горизонтальные воркеры |

**Честный вывод:** архитектура (шардирование, keyset, bounded FTS, LRU, backpressure) не имеет узких мест,
растущих с N, кроме перечисленных выше O(offset)/COUNT/частых слов. Физический предел — размер HNSW-индекса:
на обычном ПК (16–32 ГБ RAM) 2 млн документов с 1024-мерными векторами не работают. Варианты: `halfvec`,
сокращение размерности эмбеддингов, секционирование по типу документа, несколько узлов PostgreSQL. Эти варианты
не проверены в песочнице.

## Безопасность

- Пароли хранятся как bcrypt-хеши; доступ по JWT; роли admin / operator / viewer с проверкой на каждом маршруте.
- Роль нельзя задать при регистрации: новые пользователи получают `operator`, назначить admin может только администратор.
- Файлы проверяются по сигнатуре; ответы с файлами отдаются с безопасным типом (`application/octet-stream` для неизвестных
  и HTML-подобных типов), чтобы загрузка не превращалась в XSS.
- Лимит 50 МБ на файл; имена файлов очищаются; хранилище не отдаёт файлы без проверки прав.
- Журнал аудита: вход, загрузка, верификация, экспорт, административные действия.
- Перед использованием вне лаборатории: смените `SECRET_KEY` и пароль демо-пользователя, включите HTTPS на reverse-proxy,
  ограничьте доступ к порту 9001 (MinIO) сетью.

## Ограничения

- Лимиты (rate limit) считаются в памяти процесса: при нескольких воркерах лимит действует на каждый воркер отдельно.
- PostgreSQL: полнотекстовый поиск и векторный индекс pgvector требуют расширений `pg_trgm` и `vector`
  (в образе из `docker-compose.yml` они есть). Без `pg_trgm` поиск работает, но без триграммного индекса по имени файла.
- Фоновая обработка по умолчанию идёт в процессе API (`QUEUE_BACKEND=inline`). Для нагрузки используйте Celery + Redis.

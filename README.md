# IDP Platform — оцифровка и обработка документов

Веб-приложение для загрузки, распознавания, извлечения данных и поиска по документам (IDP).
Обработка **полностью локальная**: OCR, LLM (Ollama), эмбеддинги и поиск работают без внешних платных API.

Проект ИКТИБ ЮФУ. Спецификация (эталон проверки соответствия): [`AI/context/project.md`](AI/context/project.md).

---

## Возможности

- Загрузка PDF, JPG, PNG, TIFF, DOCX, TXT, MD — пакетно, до 50 МБ на файл. Тип файла проверяется по сигнатуре, а не по расширению.
- Извлечение текста: текстовый слой PDF и DOCX; для сканов — OCR (Tesseract или локальная VLM через Ollama).
- Препроцессинг сканов: выравнивание наклона, удаление синих печатей, бинаризация, поворот 0/90/180/270.
- Извлечение сущностей (ФИО, организации, даты, суммы, ИНН/ОГРН, адреса), классификация типа, резюме.
  Если LLM недоступна, работает эвристический fallback (регулярные выражения и правила).
- Поиск: полнотекстовый, семантический (`bge-m3`) и гибридный, с фильтрами.
- Split-Screen верификация: скан с подсветкой ↔ текст ↔ форма сущностей; статус «проверено».
- Вопросы по документу с указанием фрагментов-источников.
- Экспорт: JSON, CSV, DOCX, TXT, Markdown; пакетный экспорт CSV и XLSX.
- Статусы обработки в реальном времени (WebSocket), журнал аудита, роли `admin` / `operator` / `viewer`.

Отклонения от ТЗ перечислены в разделе [«Соответствие ТЗ»](#соответствие-тз).

## Установка

```bash
git clone https://github.com/Yaroslavsfedu/project_mp2.git
cd project_mp2
./scripts/bootstrap.sh
```

Установщик идемпотентен (повторный запуск безопасен, существующий `.env` не перезаписывается). Он:

1. проверяет Python 3.11+ и Node.js 20+;
2. создаёт виртуальное окружение `backend/.venv` и ставит зависимости;
3. создаёт `.env` из `.env.example` и генерирует случайный `SECRET_KEY`;
4. применяет миграции Alembic к `backend/data/idp.db` (SQLite);
5. проверяет демо-документы в `samples/`;
6. ставит зависимости фронтенда (`npm ci`);
7. выводит итоговую проверку окружения (`scripts/check_env.py`).

Локальные модели Ollama устанавливаются отдельно, потому что они занимают несколько гигабайт:

```bash
./scripts/bootstrap.sh --models   # то же + скачивание моделей под вашу видеопамять
```

`scripts/pull_models.sh` выбирает LLM по объёму VRAM: 14B от 20 ГБ, 7B от 7 ГБ, 3B от 4.5 ГБ, иначе 1.5B (CPU).
Эмбеддинги `bge-m3` скачиваются всегда; VLM `qwen2-vl:7b` для сканов — с флагом `WITH_VISION=1`.

### Установка вручную

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cd ..
cp .env.example .env
cd backend && PYTHONPATH=. alembic upgrade head && cd ..
cd frontend && npm ci && cd ..
```

## Использование

1. **Загрузка.** Раздел «Загрузка» (`/upload`) — выберите один или несколько файлов. Обработка идёт в фоне; статусы приходят по WebSocket.
2. **Проверка.** Откройте документ (`/documents/:id`): скан или текст рядом с извлечёнными сущностями. Исправьте поля и сохраните статус «проверено».
3. **Поиск.** Раздел «Поиск» (`/search`): запрос, режим `fulltext`, `semantic` или `hybrid`, фильтры по типу и статусу.
4. **Вопрос по документу.** Эндпоинт `POST /api/v1/documents/{id}/chat`: ответ сопровождается фрагментами-источниками.
5. **Экспорт.** Одного документа — JSON, CSV, DOCX, TXT или Markdown; нескольких — CSV или XLSX (`/api/v1/documents/export`).

Роли:

| Действие | `viewer` | `operator` | `admin` |
|---|---|---|---|
| Просмотр, поиск, чат, экспорт | да | да | да |
| Загрузка, верификация, перезапуск обработки | нет | да | да |
| Удаление документа | нет | только свой | любой |
| Администрирование (пользователи, аудит, качество) | нет | нет | да |

Документы общие для всех авторизованных пользователей: владелец влияет только на удаление.
Первый зарегистрированный пользователь становится `admin`, остальные — `operator`. Роль назначает администратор
(`PATCH /api/v1/admin/users/{id}`). Политика доступа описана по коду и ТЗ (RBAC по ролям); если нужна изоляция
документов по владельцу, её нужно добавить отдельно.

## OCR для сканов

Текстовый слой PDF, DOCX и TXT обрабатывается без OCR. Для сканов и фото нужен один из движков:

- **Tesseract** (CPU, быстро, есть координаты слов):
  - Ubuntu/Debian: `sudo apt install tesseract-ocr tesseract-ocr-rus`
  - macOS: `brew install tesseract tesseract-lang`
  - Windows: установщик UB-Mannheim, при установке выберите русский язык
- **VLM через Ollama** (GPU, лучше для фото, наклонов и рукописи): `WITH_VISION=1 ./scripts/pull_models.sh`,
  затем в `.env`: `OCR_ENGINE=ollama`.

Без OCR скан получает статус `failed` с понятным сообщением; остальные документы обрабатываются.

## Тестирование

Проверка делится на четыре уровня. Каждый можно запускать отдельно.

### 1. Автотесты backend

```bash
make test        # pytest -q в backend/: 168 тестов
```

Покрывают: API (документы, поиск, экспорт, админка, WebSocket), роли и права на запись, журнал аудита,
защиту загрузки (сигнатуры, размер, пустые файлы), пайплайн, LLM-fallback, векторный поиск (LRU, IVF, int8/int4,
смесь размерностей), масштабирование индексов, лимиты запросов. Тесты используют временную БД и
`RATE_LIMIT_BACKEND=memory`. Redis-тест общего счётчика пропускается, если Redis недоступен на `REDIS_URL`;
в CI поднимается сервис `redis:7`, поэтому тест выполняется.

### 2. Фронтенд

```bash
cd frontend && npx tsc --noEmit && npm run build
```

### 3. Качество распознавания и извлечения

```bash
make evaluate    # CER, WER, NER F1, точность классификации на samples/ground_truth.json
```

Отчёт: [`reports/quality/quality.md`](reports/quality/quality.md).

### 4. Сквозная проверка API

`make smoke` проходит 24 маршрута по HTTP: роли и запреты (viewer не пишет, оператор не администрирует),
граничные значения (лимиты, пустые и подменённые файлы, path traversal), курсорная и page-пагинация,
все форматы экспорта, поиск, чат, аудит. Требует запущенный backend с отключённым лимитом входа
(сценарий делает больше попыток входа, чем лимит 10/мин):

```bash
RATE_LIMIT_ENABLED=false make api            # в одном терминале
make smoke                                   # в другом; URL=http://host:port — другой адрес
```

Нагрузку проверяет отдельно `make load-test COUNT=50` (отчёт `reports/load_test.json`).

## Результаты замеров

**Качество** (демо-датасет, синтетические документы с текстовым слоем, fallback без OCR и LLM):

| Метрика | Значение | Цель ТЗ |
|---|---|---|
| CER (символы) | 0.02 % | ≤ 3 % |
| WER (слова) | 0.19 % | ≤ 8 % |
| NER F1 | 98.97 % | ≥ 85 % |
| Точность классификации | 100 % | ≥ 90 % |

Эти цифры не отражают качество на реальных сканах и с моделью Qwen. Их нужно измерить на целевом оборудовании.

**Поиск на 1000 документах** (p95, сервисный уровень, цель ТЗ < 200 мс):

| База | fulltext | semantic | hybrid |
|---|---|---|---|
| PostgreSQL 16 + pgvector | 22 мс | 8 мс | 30 мс |
| SQLite | 55 мс | 31 мс | 67 мс |

Время вычисления вектора запроса через `bge-m3` в замер не входит.

**Масштаб PostgreSQL, 2k → 100k документов** (p95, мс): список 2.1 → 2.3; keyset-пагинация 2.6 → 2.0;
offset на 50k 2.0 → 25.9; полнотекстовый поиск 14.8 → 27.1; семантика (HNSW) 3.7 → 3.0; гибрид 10.2 → 28.9.
Порог p95 < 100 мс на 100k выполнен.

**Векторный поиск, 1M векторов** (p50 / p95, мс; recall@10 — строгий / допусковый):

| Вариант | Время | Recall@10 | RSS поиска |
|---|---|---|---|
| float32, полный перебор | 6521 / 6580 | 1.00 / 1.00 | 2653 МБ |
| линейный POPCNT + int8 | 22.9 / 40.8 | 0.91 / 1.00 | 187 МБ |
| **IVF + int8 (по умолчанию)** | **4.2 / 13.0** | **0.91 / 1.00** | **80 МБ** |
| IVF + int4 | 7.2 / 14.7 | 0.54 / 0.75 | 76 МБ |

Эталон recall — точный float32-косинус. Строгий recall — совпадение позиций с точным top-10;
допусковый — точный косинус кандидата не ниже 10-го точного минус 0.01.
int4 вдвое меньше по диску, но допусковый recall заметно ниже, поэтому по умолчанию остаётся int8.

**Пайплайн обработки** (среднее на документ, 6 демо-документов без сканов):
0.20 с → 0.14 с (306 → 439 док/мин). Ускорение дали: отказ от `optimize=True` при PNG-рендере текстовых страниц
(~184 мс → ~45 мс на страницу) и отказ от лишнего `SELECT` при обновлении статуса. Замеры: `reports/pipeline_profile_{before,after}.json`.

## Масштабирование

Архитектура рассчитана на рост до 2 000 000 документов без деградации отклика списка и поиска.

| Задача | Решение | Где в коде |
|---|---|---|
| Хранение файлов | Префиксное шардирование `uploads/ab/cd/{id}_{имя}` (как объекты Git). Старые пути читаются через `document_prefixes` | `services/storage_service.py` |
| Список документов | Keyset-пагинация по `(created_at, id)` через `cursor`; `page/limit` сохранены; глубокий OFFSET ограничен | `services/document_list_service.py`, `api/v1/documents.py` |
| Индексы | Составные B-Tree `(status, doc_type, created_at DESC)` и `(created_at DESC, id)` | `models/document.py`, миграция `d5a1c9e3f7b2` |
| Счётчик списка | При ≥ 100 000 строк — оценка `pg_class.reltuples`, иначе `COUNT(*)`; кэш 30 с | `document_list_service.py` |
| Полнотекстовый поиск | Bounded-отбор кандидатов: GIN по `search_tsv`, `LIMIT 2000`; `ts_rank` и `ts_headline` только для них | `services/search_service.py`, `core/database.py` |
| Векторный поиск (PostgreSQL) | pgvector HNSW, `m=16, ef_construction=64`, `hnsw.ef_search` задаётся на запрос | `core/database.py`, `services/vector_store.py` |
| Векторный поиск (SQLite) | LRU-кэш вместо полного сброса; mmap-индекс с IVF (256 кластеров, `nprobe=8`) | `services/vector_store.py`, `services/mmap_index.py` |
| Пакетная загрузка | `bulk_ingest.py` с backpressure (ограничение очереди) | `scripts/bulk_ingest.py`, `make bulk-ingest` |

Оценка ресурсов на 2 млн документов (экстраполяция по замерам на 100k):

| Ресурс | Оценка | Комментарий |
|---|---|---|
| БД (метаданные, чанки) | ~290 ГБ | без эмбеддингов в JSON |
| HNSW float32 | ~148 ГБ | на обычном ПК не помещается |
| HNSW halfvec | ~74 ГБ | требует pgvector ≥ 0.7, не проверено |
| Оригиналы файлов | ~380 ГБ | файловая система |
| Векторы для mmap-поиска (20M чанков) | int8 19 ГБ / int4 9.5 ГБ | IVF, на поиск читается ~3 % строк |
| RAM на поиск (SQLite, IVF) | ~80–190 МБ на 1M | замер; на 2M ≈ в 2 раза больше |
| CPU, обработка | ~220 док/мин на 2 ядрах | OCR и LLM — узкое место; на 2 млн нужны горизонтальные воркеры |

**Вывод.** Шардирование, keyset-пагинация, bounded FTS, LRU и backpressure не имеют узких мест, растущих с N,
кроме перечисленных ограничений (O(offset) на очень глубоких страницах, частые слова в FTS5).
Физический предел — размер векторного индекса: на ПК с 16–32 ГБ RAM 2 млн документов с 1024-мерными векторами
в HNSW не помещаются. Варианты — `halfvec`, сокращение размерности, IVF/int8 mmap-индекс (как в SQLite-пути),
секционирование по типу документа, несколько узлов PostgreSQL. Полный замер на 2M в среде разработки не проводился.

## Безопасность

- Пароли хранятся как bcrypt-хеши. Пароли длиннее 72 байт bcrypt обрезает: различаются только первые 72 байта
  (известное ограничение bcrypt; при регистрации длина не проверяется).
- Доступ по JWT; права проверяются на каждом маршруте. Роль нельзя задать при регистрации.
- Администратор не может понизить или заблокировать себя; в системе всегда остаётся хотя бы один администратор.
- Файлы проверяются по сигнатуре; отдаются с безопасным `Content-Type` и `X-Content-Type-Options: nosniff`.
- Лимит 50 МБ на файл; имена файлов очищаются; путь к файлу не выходит за пределы хранилища.
- Журнал аудита фиксирует вход (успешный и неуспешный), регистрацию, загрузку, верификацию, перезапуск, экспорт, удаление, запуск оценки качества и административные действия.
- Перед использованием вне лаборатории: смените `SECRET_KEY` и пароль демо-пользователя, отключите `SEED_DEMO`,
  включите HTTPS на reverse-proxy, ограничьте доступ к MinIO (порт 9001) сетью.

## Ограничения

- Лимиты запросов в памяти процесса действуют на каждый воркер отдельно. Для нескольких воркеров нужен Redis (`RATE_LIMIT_BACKEND=redis`).
- Для PostgreSQL триграммный индекс по имени файла требует расширения `pg_trgm`; без него поиск работает, но медленнее по имени.
- Фоновая обработка по умолчанию идёт в процессе API (`QUEUE_BACKEND=inline`). Для нагрузки используйте Celery + Redis.
